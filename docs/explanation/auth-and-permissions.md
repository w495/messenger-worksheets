# Авторизация и границы доступа

Сервис использует три независимых вида авторизации: пользовательский
OAuth Мессенджера, OpenAI API key и авторизацию Codex CLI. Они нужны
для разных действий и хранятся у разных служб.

## Кто от чьего имени действует

Шлюзы отвечают от выбранного пользовательского аккаунта Мессенджера.
OAuth доступен шлюзам, а ожидаемый email сверяется с сервером.
Участие аккаунта в организации само по себе не определяет, подходит
ли он для развёртывания: решающей остаётся проверка идентичности.

API-worker получает OpenAI API key для обычного текста API-чата.
Общий Codex worker использует авторизацию системного пользователя
`worksheet-chat-admin`. Задачи обоих чатов расходуют его модельную квоту.
Команда `/model` меняет параметры запроса, сохраняя способ авторизации.

RPC защищён HTTPS и отдельным транспортным токеном каждого профиля.
API, резервный Local-user и общий Codex worker имеют собственные
CA, сертификаты и приватные ключи. Общий доверенный CA позволил бы
одному профилю принять сертификат другого, поэтому цепочки разделены.

Код и venv принадлежат root; runtime-пользователи не могут изменять
исполняемые исходники. Файлы окружения имеют права `0600`, состояние
служб — `0700`. Административный helper разрешает оператору только
фиксированные операции. Это право действует до явного отзыва.

## Что изолирует sandbox-worker

В установленной конфигурации задания разрешены всем участникам обоих
чатов. Все они выполняются под одним `worksheet-chat-admin`, имеют
сеть и общее состояние этого пользователя. Название sandbox-worker
обозначает профиль запуска; изоляции участников друг от друга нет.

Для задач Codex использует `danger-full-access` внутри ограничений
systemd. Домашние каталоги и дополнительные пути `/data`, `/mnt`,
`/media`, `/srv` скрыты. Служба ограничивает процессы, память и CPU.
При этом задача может читать собственную Codex-авторизацию и данные
других задач того же системного аккаунта.

Эта граница подходит чату участников, которым оператор доверяет
работу с общим аккаунтом. Подключение недоверенных участников требует
другой модели изоляции и управления секретами.

`/plan` и `/review` запускают Codex с доступом на чтение и не возвращают
созданные файлы. Они позволяют изучить входные данные инструментами
без исправлений. Отмена `/stop` завершает процессы задачи, но не
откатывает команды и внешние изменения, которые уже успели выполниться.

## Почему важны PATH и доступ к /proc

Codex получает очищенное окружение через
`shell_environment_policy.inherit="none"`. Системный
`PATH=/usr/local/bin:/usr/bin:/bin` задаётся отдельно, чтобы helper
мог найти установленный `bwrap` с профилем AppArmor.

Без этого PATH Codex 0.171.0 может выбрать встроенный `bwrap`
и завершить запуск ошибкой loopback или UID map. Исправление пути
сохраняет AppArmor и права чтения `/plan` и `/review`.

Для sandbox-worker задан `ProcSubset=all`: `bwrap` читает
`/proc/sys/kernel/overflowuid` при создании user namespace.
`ProcSubset=pid` скрывает этот файл и может приводить к ошибке
`No such file or directory`. Одновременно `ProtectProc=invisible`
ограничивает видимость чужих процессов, а `ProtectKernelTunables=yes`
запрещает запись в `/proc/sys`.

[Диагностика sandbox](../how-to/operate.md#найти-причину-ошибки)
сравнивает ограничения во временных unit, сохраняя настройки
работающей службы.
